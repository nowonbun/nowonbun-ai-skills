# Coding Assistant Skill

# Must

## Scope
- 구현 계획, 검토 또는 검증이 필요한 코드, 구성 또는 개발자 문서 변경을 처리할 때 이 문서를 적용해야 합니다.
- 실행 동작에 영향을 줄 수 있는 문서 및 구성 변경에도 동일한 검토 원칙을 적용해야 합니다.

## Source of Truth
- 이 문서는 `./SKILL.md`에 있는 코딩 변경 조정, 변경 위험 프레임워크, Codex 중심 실행 범위, 로컬 검증 계획 및 결과 보고 구조를 규정합니다.
- 이 문서는 외부 교차 검토 런타임, 외부 검토 로그 스키마 또는 일반적인 스킬 문서 형식 규칙을 규정하지 않습니다.
- 외부 검토는 사용자가 명시적으로 요청한 경우에만 해당 검토 도구의 전용 스킬 또는 운영 규칙을 참조해야 합니다.

## Change Classification Rules
- 구현 전에 각 요청을 비파괴적 또는 파괴적 변경으로 분류해야 합니다.
- 스키마 변경, API 계약 변경, 인증 또는 권한 변경, 대규모 삭제 및 워크플로를 방해하는 구성 변경은 파괴적 변경으로 처리해야 합니다.
- 분류에 따른 승인 요구 사항을 문서화해야 합니다.

## Assistance Rules
- 요구사항 분석, 영향 범위 식별, 구현 계획, 변경 실행, 로컬 검증 및 최종 보고를 하나의 실행 흐름으로 담당해야 합니다.
- 사용자 요청과 저장소 증거를 기준으로 작업 범위를 좁혀야 합니다.
- 변경 전 계획과 변경 후 검증을 같은 대화 흐름에서 추적해야 합니다.
- 검증할 수 없는 주장과 실행하지 않은 검증 명령을 검증된 사실과 분리해서 표시해야 합니다.
- 고위험 변경에서 독립 검토가 요구되면 즉시 실행을 중지하고 사용자에게 외부 검토 요청 여부를 확인해야 합니다.

## Approval and Execution Rules
- 파괴적인 변경을 수행하기 전에 사용자 승인을 받아야 합니다.
- 파괴적인 변경을 실행하기 전에 계획된 파일 범위와 예상되는 영향을 제시해야 합니다.
- 코드, 문서 또는 구성 쓰기를 포함하는 작업은 변경 목적, 대상 파일 및 검증 방법이 확인된 후에만 `apply_patch`, 셸 기반 쓰기 또는 기타 쓰기 도구를 실행해야 합니다.
- MCP, 문제 이력, 데이터베이스 상태 또는 외부 문서가 필요한 경우 증거 경로를 명시해야 합니다.

## Verification Rules
- 변경된 파일의 문법, 형식, 테스트 및 영향 범위에 맞는 검증 명령을 식별해야 합니다.
- 실행한 검증 명령의 결과를 기록해야 합니다.
- 검증 명령을 실행하지 못한 경우 실패 원인과 남은 위험을 기록해야 합니다.
- 사용자 또는 저장소 규칙이 외부 검토를 필수로 지정한 경우 외부 검토 완료 전까지 완료 상태를 보고해서는 안 됩니다.
- 외부 검토가 요청되었으나 실행할 수 없는 경우 차단 상태, 실패 원인 및 재실행 조건을 보고해야 합니다.

## Final Reporting Rules
- 변경된 파일, 주요 수정 사항, 영향 범위, 검증 명령 및 남은 문제를 보고해야 합니다.
- 외부 검토가 사용자 또는 저장소 규칙에 의해 요구되었는지 여부와 실행 결과를 보고해야 합니다.
- 최종 보고서에서 검증된 사실과 검증되지 않은 가정을 구분해야 합니다.

# Must NOT

## Prohibited Execution Behavior
- 사용자 승인 전에 파괴적인 변경을 구현해서는 안 됩니다.
- 변경 목적, 대상 파일 및 검증 방법이 확인되기 전에 코드, 문서 또는 구성 쓰기를 시작해서는 안 됩니다.
- 계획만 존재하는 상태에서 검증이 완료된 것으로 표시해서는 안 됩니다.
- 검증 실패, 시간 초과 또는 미실행 상태를 숨겨서는 안 됩니다.
- 실행 결과와 검증 결과를 레이블이 없는 하나의 블록으로 병합해서는 안 됩니다.
- 실행 동작을 변경하는 구성 또는 문서 변경 사항을 검토가 필요 없는 변경 사항으로 처리해서는 안 됩니다.
- 사용자 또는 저장소 규칙이 외부 검토를 필수로 지정하지 않았는데도 외부 검토를 기본 관문으로 설정해서는 안 됩니다.

# Flow

## Change Handling Flow
1. 요청을 비파괴적 또는 파괴적 요청으로 분류합니다.
2. 대상 파일, 예상 영향 및 승인 요구 사항을 정의합니다.
3. 쓰기 작업이 포함되는 경우 변경 목적, 대상 파일 및 검증 방법을 확정합니다.
4. 파괴적 변경이면 사용자 승인을 받은 뒤 변경을 실행합니다.
5. 비파괴적 변경이면 확정된 범위 안에서 Codex가 변경을 실행합니다.
6. 변경 후 검증 명령을 실행하거나 미실행 사유를 기록합니다.
7. 외부 검토가 필수로 지정된 경우 외부 검토 결과를 확보하거나 차단 상태를 보고합니다.
8. 변경된 파일, 검증 증거, 외부 검토 요구 여부 및 잔여 위험 요소를 보고합니다.

# Definition of Done

## Verification
- 변경 분류 및 승인 요구 사항이 문서화되어 있습니다.
- Codex 중심 실행 흐름에서 요구사항 분석, 구현, 검증 및 보고 책임이 추적됩니다.
- 사용자 승인을 받을 때까지 파괴적인 변경은 차단됩니다.
- 변경 목적, 대상 파일 및 검증 방법이 확인되기 전에는 코드, 문서 또는 구성 쓰기가 차단됩니다.
- 외부 검토가 필수인지 여부와 실행 결과 또는 차단 상태가 기록됩니다.
- 최종 보고서에는 변경된 파일, 영향 범위, 검증 명령 및 남아 있는 위험이 포함됩니다.

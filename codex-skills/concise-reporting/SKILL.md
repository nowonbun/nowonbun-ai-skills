# Concise Reporting

# Must

## Scope
- 사용자에게 완료 보고, 상태 보고, 실패 보고, 검증 보고 또는 결정 요청을 작성할 때 이 문서를 적용해야 합니다.
- 이 문서는 사용자-facing 응답의 길이, 항목 선택, 증거 표시 및 누락 방지 기준을 규정합니다.
- 이 문서는 작업 수행 방식, 도구 선택, 코드 수정 방식 또는 검증 명령 자체를 규정하지 않습니다.

## Core Rules
- 보고서는 결론을 첫 문장에 배치해야 합니다.
- 보고서는 기본적으로 4개 이하의 불릿으로 작성해야 합니다.
- 각 불릿은 하나의 사실 또는 하나의 요청만 포함해야 합니다.
- 각 불릿은 1줄로 작성해야 합니다.
- 보고서에는 사용자가 다음 행동을 결정하는 데 필요한 정보만 포함해야 합니다.
- 완료 보고에는 변경 대상, 핵심 변경, 검증 결과를 포함해야 합니다.
- 실패 보고에는 실패 지점, 증거, 다음 행동을 포함해야 합니다.
- 중지 조건 보고에는 차단 사유, 필요한 사용자 결정, 선택지별 영향을 포함해야 합니다.
- 파일 작업 보고에는 수정한 파일 경로만 포함해야 합니다.
- 검증 결과는 실행 로그, 파일 경로, 도구 응답 또는 명령 출력 중 하나 이상의 증거로 뒷받침해야 합니다.
- 세부 설명이 필요한 경우에도 먼저 요약을 제시하고, 세부 내용은 `세부` 제목 아래에 분리해야 합니다.

## Length Rules
- 일반 완료 보고는 6줄 이하로 작성해야 합니다.
- 오류 또는 차단 보고는 8줄 이하로 작성해야 합니다.
- 사용자가 상세 설명을 요청한 경우에만 8줄을 초과할 수 있습니다.
- 상위 규칙이 필수 보고 필드를 요구하는 경우, 해당 필드는 생략하지 말고 가장 짧은 문장으로 작성해야 합니다.

## Accuracy Rules
- 확인하지 않은 내용을 사실로 쓰면 안 됩니다.
- 추정이 필요한 경우 `미확인`으로 표시해야 합니다.
- 검증하지 않은 성공을 완료로 보고하면 안 됩니다.
- 파일이나 명령 증거가 있는 경우, 증거는 경로 또는 로그 요약으로 표시해야 합니다.
- 사용자 요청 범위 밖의 변경 또는 관찰은 보고하지 말아야 합니다.

# Must NOT

## Verbosity
- 작업 절차 전체를 사용자가 요청하지 않았는데 나열해서는 안 됩니다.
- 변경하지 않은 파일 목록을 보고해서는 안 됩니다.
- 성공한 내부 준비 단계와 스킬 적용 이유를 최종 보고에 반복해서는 안 됩니다.
- 같은 의미의 성공 표현을 여러 문장으로 반복해서는 안 됩니다.
- 사용자의 다음 행동에 영향을 주지 않는 부가 정보를 포함해서는 안 됩니다.

## Accuracy
- 증거 없는 단정 표현을 사용해서는 안 됩니다.
- 실패나 미검증 상태를 간결성을 이유로 생략해서는 안 됩니다.
- 필수 보고 형식의 필드를 줄이기 위해 제거해서는 안 됩니다.

# Flow

1. 보고 목적을 완료, 상태, 실패, 검증 또는 결정 요청 중 하나로 분류합니다.
2. 사용자가 결정을 내리는 데 필요한 사실만 선택합니다.
3. 결론을 첫 문장으로 작성합니다.
4. 증거가 필요한 항목에 경로, 로그 요약 또는 도구 응답을 붙입니다.
5. 중복 문장, 내부 절차, 감정 표현을 제거합니다.
6. 줄 수 제한과 필수 필드 보존 여부를 확인합니다.

# Definition of Done

## Verification
- 첫 문장이 결론입니다.
- 일반 완료 보고는 6줄 이하입니다.
- 오류 또는 차단 보고는 8줄 이하입니다.
- 각 불릿은 하나의 사실 또는 하나의 요청만 포함합니다.
- 검증 결과는 최소 하나의 증거를 포함합니다.
- 미검증 내용은 `미확인`으로 표시됩니다.
- 필수 보고 형식의 필드는 생략되지 않았습니다.
- 사용자 요청 범위 밖의 정보가 제거되었습니다.

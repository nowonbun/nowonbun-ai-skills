# Source Code TDD Rule

# Must

## Scope
- 이 스킬은 관찰 가능한 동작 변경, 결함 수정 또는 안정성이 필요한 공개 계약 변경에 적용해야 합니다.
- 조사, 읽기 전용 분석, 생성 코드 재동기화, 의미 없는 재서식에는 실패 테스트 선행을 요구해서는 안 됩니다.

## Test Selection
- 결함 수정에는 가능하면 결함을 재현하는 실패 테스트를 먼저 추가해야 합니다.
- 새 동작에는 성공 경로와 변경으로 영향을 받는 경계·오류 경로를 검증해야 합니다.
- 기존 테스트로 계약을 충분히 관찰할 수 있으면 같은 oracle의 테스트를 중복 추가해서는 안 됩니다.
- 외부 시간, 난수, 네트워크 또는 파일 시스템이 테스트 안정성을 해치면 제어 가능한 경계로 분리해야 합니다.
- 공개 인터페이스 변경에는 호환성 검증, 마이그레이션 또는 폐기 계획 중 해당하는 조치를 포함해야 합니다.
- 테스트를 실행할 수 없으면 사유와 검증되지 않은 위험을 보고해야 합니다.

# Must NOT

## Test Theater
- 테스트 통과를 위해 검증 대상 동작을 삭제하거나 약화해서는 안 됩니다.
- 실제 오류를 숨기는 광범위한 mock, 임의 재시도 또는 예외 무시를 사용해서는 안 됩니다.
- 모든 변경에 단위·통합·E2E·성능 테스트를 동시에 요구해서는 안 됩니다.
- 월별 보고, 메트릭 또는 테스트 예산을 프로젝트 근거 없이 의무화해서는 안 됩니다.
- 실패하거나 불안정한 테스트를 근거 없이 삭제하거나 건너뛰어서는 안 됩니다.

# Flow

1. 관찰할 계약과 변경 위험을 확인합니다.
2. 기존 테스트가 충분한지 확인하고 부족하면 최소 실패 또는 회귀 테스트를 추가합니다.
3. 최소 구현 후 영향 범위에 해당하는 검증만 실행합니다.
4. 결과와 남은 위험을 보고합니다.

# Definition of Done

## Verification
- 결함과 동작 변경은 관찰 가능한 테스트로 검증됩니다.
- 테스트 계층은 변경 범위에 비례합니다.
- 중복 테스트와 프로젝트 근거 없는 운영 의무가 없습니다.
